What the code promises.

  • A node fails. Nothing acknowledged is lost.

    Malachi acknowledges a write only after a majority of the segment's copies have fsynced it. With three copies, one node can fail and every acknowledged record is still on the other two.

  • Split a hot range without copying data.

    A split seals the range's active segment and gives each half of its keyspace to a new child. It is a metadata change: no segment is copied or rewritten, and merges happen only between buddy halves.

  • Your client's cursor never changes shape.

    Clients hold topics, keys and an opaque cursor. Splits and merges happen underneath; a read drains the parent's sealed data before the child's, so records with the same key stay in order.

  • Metadata agreed by Raft.

    Topic, range and segment metadata lives in Raft groups on ra, inside each node. Records stay out of Raft: the primary ships them to its followers in batches.

The model

A range grows, divides, and seals what it leaves behind.

Inside a topic

See where every record lives.

Highlight

Topic

A topic is a keyspace divided into ranges. Its active ranges cover the keyspace exactly once, and they split and merge at runtime. Here, range 1 split into ranges 2 and 3.

Range

A range owns one block of the keyspace. Every record whose key lands in that block is appended to it, in a sequence of segments. After a split the sealed parent stays as history its children read through.

Segment

The unit of replication. The active segment takes appends at its write position; a sealed segment is immutable, and retention deletes the oldest first.

Record

A record frame: a short header, then the payload its CRC32 covers: key, value and headers. Malachi does not interpret the value.

What you get

The NorthGuard shape, on the BEAM.

Ranges instead of partitions

A record's key hashes to a position in the topic's keyspace, and that position falls in exactly one range. Split and merge are metadata operations: segments are never physically combined or copied, and a merge happens only between buddy ranges. Same-key ordering survives resharding.

Segments with a lifecycle

A segment is the unit of replication. It takes appends while active and becomes immutable once sealed, by size, by age, or on failure. Every record frame carries a checksum, and a scrubber re-verifies sealed segments and rebuilds a damaged copy from a replica that still verifies.

A Raft control plane

Topic, range and segment metadata lives in vnodes, each a Raft group on ra, sharded on a hash ring by topic. Records do not go through Raft: the primary ships batches to its followers and acknowledges a write once a quorum has fsynced it.

Auth and ACLs

Every producer and consumer authenticates. Users and per-topic ACLs are replicated across the cluster in their own Raft group. Passwords are hashed with Argon2, TLS is required in production, nodes can talk over mutual TLS, and failed logins lock an account out progressively.

How it works

Three steps, one cursor.

  1. 01

    Produce to a range

    The key routes each record to the one range that owns its slice of the keyspace. When a range gets busy it splits at the midpoint of its keyspace: its segment is sealed, and each half goes to a new child range.

  2. 02

    Replicate and seal

    The primary ships each batch to its followers and acknowledges it once a majority has fsynced it. A full, old or failed segment is sealed on every copy and never edited again.

    active ─ 1 GB · 1 h · failure ─▶ sealed

  3. 03

    Consume from a cursor

    A fetch returns records and an opaque cursor; pass it back to resume. After a split, the read drains the parent's sealed records first, then follows its key into the child.

Compared

How Malachi differs from the logs you know.

Grow a hot topic without moving its keys.

Apache Kafka

  • Partitions can be added but not removed.
  • Adding partitions does not move existing records, so a key's new records can go to a different partition than its old ones.
  • Consumers track one offset per partition.
  • A write commits once every in-sync replica (ISR) has it.

Malachi

  • Ranges split and merge at runtime.
  • A key always maps to the one range that contains it, and reads drain the parent before the child.
  • Clients hold an opaque cursor.
  • A write is acknowledged once a majority of copies have fsynced it.

Sources: Kafka docs, Basic operations · Kafka docs, Design · Confluent Platform docs

Shrink back when traffic drops.

Redpanda

  • Speaks the Kafka API: a keyed record goes to the partition its key hashes to.
  • Partitions can be added; existing records are not redistributed to them.
  • The partition count of a topic cannot be reduced.

Malachi

  • Cold buddy ranges merge back, as a metadata change.
  • No segment is copied by a split or a merge.
  • Clients do not see either.

Source: Redpanda docs, Manage Topics

One system to run.

Apache Pulsar

  • A cluster runs brokers, BookKeeper bookies and a metadata store (Oxia is recommended for new clusters; ZooKeeper is supported).
  • Classic partitioned topics only grow, and resizing them can remap keys.
  • Since Pulsar 5.0 (released October 5, 2026), scalable topics split and merge key ranges, for clients on the v5 API (Java today).

Malachi

  • Each node runs one Elixir application; the Raft control plane runs inside it.
  • Ranges split and merge for every client.
  • Clients hold topics, keys and a cursor.

Sources: Pulsar docs, Architecture · Pulsar docs, Manage topics · Pulsar 5.0 docs, Scalable topics · Pulsar 5.0 release announcement

Run Malachi on your machine.

Malachi listens on 4040 and the dashboard on 4041. It is in active development and not production-ready.

Quickstart
# Set your own admin password (12 characters or more) in the shell first:
# export MALACHI_ADMIN_PASS='your own password'
docker run \
  -p 127.0.0.1:4040:4040 \
  -p 127.0.0.1:4041:4041 \
  -e MALACHI_ADMIN_PASS \
  -e MALACHI_REQUIRE_TLS=false \
  hectorcardoso/malachi:latest
